# Design Principles

Архитектурный подход Build System опирается на несколько принципов. Каждое решение, описанное в остальной документации, — следствие одного или нескольких из них.

## Архитектура определяет инструменты

Gulp и Nunjucks выбраны не потому, что они обязательны, а потому, что реализуют уже сформировавшийся архитектурный подход. Появятся более подходящие инструменты — подход останется прежним.

## Один элемент — одна ответственность

- **Pages** — точки входа приложения.
- **Sections** — структура отдельных страниц.
- **Components** — повторно используемые элементы интерфейса.
- **Templates** — инфраструктурные шаблоны.
- **Data** — источник данных для шаблонов.

Такое разделение делает архитектуру предсказуемой — именно поэтому ниже, в разделах про каждую сущность, не повторяется отдельное обоснование "почему она выделена отдельно": причина всегда эта.

## Структура проекта должна быть очевидной

Разработчик, впервые открывший проект, должен понимать назначение каталогов по их именам и месту в дереве — без необходимости читать документацию или исходный код.

## Повторное использование — часть архитектуры, а не опция

Архитектура изначально строится так, чтобы переиспользование Components, Sections и Templates было естественным следствием структуры, а не отдельной практикой, которую нужно поддерживать вручную.

## Build System понимает архитектуру, а не только файлы

Build System оперирует не файлами, а архитектурными сущностями — страницами, секциями, компонентами, шаблонами и связями между ними. Именно это даёт более высокий уровень автоматизации, чем обработка файлов по маске.

## Любая зависимость должна быть известна системе

Связи между сущностями должны быть доступны Build System — это основа Dependency Graph и точечной пересборки только затронутых страниц.

## Производительность — следствие архитектуры

Incremental Build возможен не потому, что это отдельная оптимизация, а потому, что Build System уже знает архитектуру проекта и все зависимости между её элементами.
