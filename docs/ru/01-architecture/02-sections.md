# Sections

Sections являются основными строительными блоками страниц.

Каждая Section представляет собой самостоятельную функциональную область интерфейса, объединяющую связанные элементы, компоненты и данные в рамках одной задачи.

## Ответственность

Section отвечает за реализацию отдельной части страницы.

Например:

- Hero;
- About;
- Services;
- Gallery;
- Contacts.

Section определяет внутреннюю структуру своей области, но не отвечает за построение всей страницы.

Композиция страницы является ответственностью Page.

## Композиция

Page формируется путём композиции независимых Sections.

Каждая Section представляет собой самостоятельную функциональную область и не зависит от своего расположения внутри страницы.

Такой подход позволяет свободно изменять структуру страниц, повторно использовать Sections и масштабировать проект без изменения существующей архитектуры.

## Организация

Build System поддерживает два способа организации Sections в зависимости от структуры проекта.

### Landing Page

Для небольших проектов Sections могут располагаться непосредственно в каталоге `src/views/sections`.

```text
src/views/sections/
├── _hero.njk
├── _about.njk
├── _services.njk
├── _gallery.njk
└── _contacts.njk
```

### Многостраничный проект

Для более крупных проектов рекомендуется группировать Sections по функциональным областям или страницам.

```text
src/views/sections/
├── about/
│   ├── _hero.njk
│   ├── _about.njk
│   └── _team.njk
├── contacts/
│   ├── _hero.njk
│   └── _contacts.njk
└── services/
    ├── _hero.njk
    └── _services.njk
```

Такой подход позволяет сохранять понятную структуру проекта независимо от его масштаба.

## Соглашение об именовании

Все Sections используют единые соглашения об именовании.

Имя файла начинается с символа `_`, а само имя отражает назначение соответствующей функциональной области.

При использовании группировки одинаковые имена Sections допускаются в разных каталогах, поскольку они принадлежат разным архитектурным областям.

## Доступ через Template API

Sections подключаются через Template API.

Разработчик указывает не путь к файлу, а архитектурный адрес Section.

Для Landing Page:

```njk
{% include getSection("", "about") %}
```

Для многостраничного проекта:

```njk
{% include getSection("about", "hero") %}
```

Build System самостоятельно определяет физическое расположение шаблона.

Благодаря этому шаблоны не зависят от структуры каталогов, а изменение организации проекта не требует изменения существующих вызовов.

## Взаимодействие с Components

Section может использовать один или несколько Components.

При этом Section отвечает за организацию компонентов внутри своей области, а Components отвечают только за собственную функциональность.

Такое разделение позволяет сохранить чёткие границы ответственности между архитектурными сущностями.

## Взаимодействие с данными

Section может использовать данные, предоставляемые через Template API.

Источник данных не влияет на архитектурную роль Section и остаётся частью соответствующей архитектурной сущности.

## Почему Sections существуют отдельно

Во многих проектах крупные части страниц реализуются как обычные include-шаблоны.

В данном архитектурном подходе Section является самостоятельной архитектурной сущностью со своей областью ответственности.

Такое разделение делает структуру проекта более понятной, упрощает сопровождение и позволяет Build System работать с архитектурной моделью проекта, а не с отдельными файлами.
